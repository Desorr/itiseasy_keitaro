# Менеджер кампаний Keitaro

FastAPI / Python 3.11 / httpx и React / TypeScript / Vite. Кампании и распределение трафика работают в Keitaro. PostgreSQL хранит импортированные кампании приложения, потоки, известные офферы, историю их привязок, закрепления и неопубликованные черновики. Все обращения к Keitaro и PostgreSQL асинхронные: `httpx.AsyncClient`, SQLAlchemy `AsyncSession`, `asyncpg`.

## Настройка и запуск

В корневом `.env` задайте:

```dotenv
KEITARO_BASE_URL=https://your-tracker.example
KEITARO_API_KEY=your_key
POSTGRES_DB=keitaro
POSTGRES_USER=keitaro
POSTGRES_PASSWORD=replace_with_random_hex_password
POSTGRES_PORT=55432
DATABASE_URL=postgresql+asyncpg://keitaro:replace_with_random_hex_password@127.0.0.1:55432/keitaro
```

Для пароля рекомендуется случайная hex-строка; специальные символы в DATABASE_URL должны быть URL-кодированы. `.env` исключён из Git. API-ключ и данные подключения остаются на backend. `KEITARO_BASE_URL` принимает HTTPS-origin, в том числе с окончанием `/admin` или `/admin_api/v1`.

```sh
docker compose up -d --build
docker compose ps
```

Compose запускает PostgreSQL 17, применяет `alembic upgrade head` и запускает backend, затем frontend. Данные БД сохраняются в именованном томе `postgres_data`; обычные перезапуски и `docker compose down` его не удаляют. PostgreSQL доступен только на `127.0.0.1:55432` (порт можно изменить через POSTGRES_PORT). В контейнере backend Compose переопределяет DATABASE_URL, используя имя сервиса `postgres`.

- [Приложение](http://localhost:8080)
- [Swagger](http://localhost:8000/docs)
- [Готовность backend и PostgreSQL](http://localhost:8000/api/health)

Ключу Keitaro нужны права чтения доменов, источников, групп, офферов, кампаний и потоков; создания групп, кампаний и потоков; обновления потоков; активации и архивирования кампаний. Смена трекера требует отдельной БД: ID в хранилище относятся к одному экземпляру Keitaro.

Локальный запуск (Python 3.11+, Node.js 22.12+ или 24+):

```sh
docker compose up -d postgres
python3 -m venv venv
venv/bin/pip install -r backend/requirements.txt
cd backend
../venv/bin/alembic upgrade head
../venv/bin/uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd frontend
npm ci
npm run dev
```

Откройте [localhost:5173](http://localhost:5173). Для изменений схемы используются миграции Alembic в `backend/migrations`. Таблицы при старте автоматически не пересоздаются.

## Создание и список кампаний

Пользователь вводит название 5–255 символов, один существующий двухбуквенный GEO-код и выбирает активный оффер из списка. Поиск в поле выполняется только по цифровому ID. Список доступных офферов загружается один раз после первого фокуса; выбор из него обязателен. Доступность выбранного оффера дополнительно проверяется сервером.

Домен и источник — первые активные из ответов `GET /domains` и `GET /traffic_sources`. Все новые кампании используют общую группу `test_markovskiy_group`: приложение получает её через API или создаёт при отсутствии.

Создаётся выключенная кампания типа `position`, с `uniqueness_method=ip_ua`, `cost_currency=USD`, `cost_auto=true` и двумя потоками:

1. `Flow 1` — regular, позиция 1: выбранная страна → HTTP-редирект на `https://google.com`.
2. `Flow 2` — regular, позиция 2: остальные посетители → выбранный оффер, доля 100%.

Имена генерируются последовательно при создании потоков (Flow 1, Flow 2), без фиксированных ID. Дополнительные потоки (Flow 3 и далее) создаются в самом Keitaro; в приложении нет функции их создания. Импорт отображает их фактические названия. Существующие потоки автоматически не переименовываются.

После чтения и проверки конфигурации кампания активируется и импортируется в PostgreSQL. `Idempotency-Key` с UUID формирует alias `tm_<16 hex>`; автоматически повторять создание нельзя. При частичном создании известный ID возвращается в ошибке; список нужно синхронизировать перед следующей попыткой.

При открытии страницы и по кнопке «Обновить» приложение синхронизирует с Keitaro только свои кампании с alias `tm_…`, включая потоки и офферы. При недоступности Keitaro интерфейс показывает ошибку и пытается загрузить сохранённый список из БД. Чтение сохранённого списка само по себе не обновляет Keitaro.

Интерфейс приложения и сообщения об ошибках отображаются на английском языке.

## Редактор

В карточке кампании доступны «Edit» и «Delete campaign». При каждом входе в редактор список потоков и офферов изначально пуст: данные отображаются только после нажатия «Fetch streams from KT». Сохранённые черновики и архив при этом остаются в БД и загружаются вместе с потоками. В редакторе кнопка «Add campaign» справа снизу скрыта. Название, GEO и настройки самих потоков не редактируются.

Сначала отображаются потоки с известными офферами; потоки без офферов идут внизу с названием из Keitaro и ID, без фильтров и редиректов. При отсутствии названия используется Flow N (N — позиция в Keitaro). Внутри каждой группы сохраняется порядок Keitaro. Потоки с офферами показывают ID, названия, доли и действия:

- **Добавить** — выбрать активный оффер по цифровому ID и добавить в черновик. Дубликаты запрещены; для архивного оффера используется «Bring back».
- **Remove** — убрать привязку в черновике; строка становится серой, доля — 0%. Последний действующий оффер не удаляется.
- **Bring back** — вернуть оффер из архива в черновик, если сам оффер доступен и активен в Keitaro.
- **Закрепить / Открепить** — сохранить текущую долю в приложении. Само закрепление не изменяет Keitaro и не требует публикации. Если закрепление меняется внутри черновика, оно отменяется вместе с черновиком.
- **Push to KT** — передать только массив `offers` выбранного потока через `PUT /streams/{id}` и проверить результат чтением. Удалённые привязки остаются в архиве PostgreSQL; объекты офферов в Keitaro не удаляются.
- **Cancel** — удалить черновик и принять последнее подтверждённое состояние. Новые неопубликованные привязки исчезают.

Изменённый поток подсвечивается жёлтым. Черновики и архив сохраняются в PostgreSQL после перезапуска; «Назад» сохраняет черновик.

При изменении состава доли незакреплённых действующих офферов делят оставшийся процент поровну. Доли целые, сумма — 100%; остаток округления распределяется в стабильном порядке (34/33/33). Закреплённые доли сохраняются. Удаление снимает закрепление; возврат выполняется без него. Если на незакреплённые офферы не остаётся хотя бы по 1%, изменение отклоняется с предложением снять закрепление. Выключенные в Keitaro привязки показываются отдельно и не получают трафик при пересчёте.

## Синхронизация, конфликты и сбои

«Fetch streams from KT» импортирует фактические привязки и доли. Известные привязки, исчезнувшие в Keitaro, остаются в архиве с долей 0% и кнопкой «Bring back». До первого импорта история удалений неизвестна. Импорт принимает фактические доли Keitaro без пересчёта и создания черновика: жёлтая подсветка и кнопки публикации/отмены от самого импорта не появляются. Офферы с положительной долей отображаются сверху, удалённые — снизу. Пересчёт и жёлтый черновик появляются только после действий пользователя в редакторе (добавление, удаление, возврат). При последующих действиях закреплённая доля берётся из импортированного состояния.

Если поток изменился снаружи при наличии черновика, приложение сохраняет актуальное состояние и черновик, показывает конфликт и блокирует публикацию. «Cancel» удаляет черновик и принимает состояние Keitaro. Изменение или исчезновение потока также проверяется перед публикацией. Keitaro не предоставляет атомарного условного обновления потока, поэтому внешнюю запись в коротком промежутке между проверкой и PUT полностью исключить нельзя.

Ревизии и блокировка кампании в PostgreSQL защищают от одновременных правок и публикаций из нескольких вкладок. Устаревшая ревизия возвращает HTTP 409. Намерение публикации сохраняется до PUT. После таймаута или перезапуска запись не повторяется автоматически; результат проверяется чтением. До завершения проверки повторная публикация и отмена заблокированы. Для прерванного запроса сверка разрешается через `2 × KEITARO_TIMEOUT_SECONDS + 10` секунд после начала публикации (по умолчанию 50 секунд). После сверки совпавший результат подтверждается, иначе сохраняется черновик; при отличии от исходного состояния показывается конфликт.

Keitaro и PostgreSQL не образуют общую транзакцию. Если запись в Keitaro прошла, а фиксация в БД не удалась, интерфейс не показывает подтверждённый успех; следующая сверка восстанавливает состояние по сохранённому намерению публикации. Ошибки содержат `code`, `message`, `uncertain`, `campaign_id`, без ключей и строк подключения.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Конфигурация и доступность PostgreSQL |
| `GET /api/offers?query=…` | Активные офферы напрямую из Keitaro |
| `GET /api/campaigns` | Сохранённые действующие кампании из PostgreSQL |
| `POST /api/campaigns/sync` | Импорт кампаний приложения и потоков из Keitaro |
| `POST /api/campaigns` | Создание; заголовок `Idempotency-Key` с UUID |
| `DELETE /api/campaigns/{id}` | Архивирование кампании в Keitaro и БД |
| `GET /api/campaigns/{id}/streams` | Потоки редактора, черновики, архив и ревизии |
| `POST /api/campaigns/{id}/streams/sync` | Обновление потоков из Keitaro |
| `PATCH /api/campaigns/{id}/streams/{sid}/draft` | Действие над черновиком |
| `DELETE /api/campaigns/{id}/streams/{sid}/draft` | Отмена черновика |
| `POST /api/campaigns/{id}/streams/{sid}/publish` | Публикация одного потока |

Пример создания:

```json
{"name": "test_markovskiy_campaign1", "geo_code": "DE", "offer_id": 123}
```

Пример действия над черновиком:

```json
{"expected_revision": 2, "action": "add", "offer_id": 456}
```

Действия: `add`, `remove`, `restore`, `toggle_pin`. Отмена и публикация принимают JSON `{"expected_revision": 3}`. Все ID положительные; ревизия обязательна. Ответ потока содержит `id`, `name`, `position`, `revision`, `editable`, `missing`, `dirty`, `conflict`, `publication`, `allocation_error`, `offers`. `allocation_error` содержит пояснение, если закрепления мешают распределению. В строке оффера: `offer_id`, `name`, `share`, `state`, `pinned`, `removed`. Объект кампании дополнен `offer_ids`; одиночное `offer_id` сохранено для совместимости и равно `null`, когда офферов несколько.

## Архивирование кампании

Удаление подтверждается небольшим диалогом «Remove» / «Cancel». Вызывается только `DELETE /campaigns/{id}`, затем проверяется результат. Перед записью проверяется принадлежность приложению. Группа `test_markovskiy_group`, офферы, домены и источники сохраняются. `/campaigns/clean_archive` не используется: он очищает весь архив трекера.

В PostgreSQL кампания помечается архивной и скрывается из списка; её история сохраняется. Повторное удаление отсутствующей или архивной кампании успешно. После успеха карточка исчезает без уведомления.

## Проверки

Автотесты и тестовые зависимости не используются по требованию проекта. Разрешены:

```sh
cd frontend && npm run build
venv/bin/python -m compileall -q backend/app backend/migrations
```

Команды выполняются из соответствующих каталогов (Python — из корня). Функциональные проверки с изменениями Keitaro выполняются только на кампаниях с префиксом `test_markovskiy_`. Для проверки оформления реальные кампании не создаются.

Документация: [Keitaro Admin API](https://docs.keitaro.io/en/development/admin-api.html), [схема API](https://admin-api.docs.keitaro.io/openapi.json), [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).
