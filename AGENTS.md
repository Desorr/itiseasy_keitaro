# Инструкции агенту

Этот файл задаёт правила изменений и проверок. Описание приложения и инструкция
запуска находятся в [README.md](README.md).

## Общие правила

- Общайтесь кратко по-русски. UI, ошибки и валидация — на английском.
  Имена кампаний и офферов не переводите.
- Решайте только поставленную задачу, без дополнительных функций и несвязанного рефакторинга.
- Backend: Python 3.11, FastAPI, httpx.AsyncClient, SQLAlchemy AsyncSession,
  asyncpg, PostgreSQL 17. Frontend: React, TypeScript, Vite.
- Сохраняйте асинхронные обращения к Keitaro и БД; не блокируйте обработчики
  сетевыми вызовами. Изменения схемы — через Alembic.
- Проверяйте ввод на frontend и backend, показывайте ошибки рядом с полями.
  При изменении API обновляйте Pydantic и TypeScript-контракты вместе.
- Зависимости добавляйте по необходимости: Python только в `backend/requirements.txt`,
  npm с сохранением `frontend/package-lock.json`.
- При изменении поведения, API, конфигурации или запуска обновляйте README.
- Коммит и push выполняйте только по запросу пользователя.

## Где менять код

- `backend/app/main.py` — маршруты, ошибки и lifecycle; `keitaro.py` — HTTP-клиент и кэш.
- `backend/app/services.py` — создание/архивирование; `editor.py` — импорт, черновики и публикация.
- `backend/app/database.py` — модели/подключение; `schemas.py` — контракты; `config.py` — настройки.
- `backend/migrations` — миграции; `docker-compose.yaml` — сервисы.
- `frontend/src/App.tsx` — список, создание и восстановление запроса;
  `CampaignEditor.tsx` — редактор; `OfferPicker.tsx` — выбор оффера;
  `api.ts` — клиент/типы; `style.css` — оформление.

## Обязательные условия: кампании

- Список/sync возвращают массив `CampaignSummary`, создание — один объект,
  только `id/name/alias/state`. `CampaignRead` — внутренний снимок backend/БД;
  не раскрывайте в этих ответах настройки и служебные ссылки.
- Alias `tm_<16 hex>` нужен для распознавания своих кампаний и восстановления
  создания. Проверяйте принадлежность перед изменением/архивированием;
  alias не секрет и не средство авторизации.
- При входе показывайте список БД до фоновой синхронизации; Refresh принудительно
  синхронизирует. Не задерживайте сохранённый список до полного импорта.
- При каждом открытии создания запрашивайте свежие активные офферы из Keitaro,
  без постоянного кэша и подмены данными БД. Поиск локальный по цифрам ID,
  выбор из dropdown обязателен, ошибка допускает Retry.
- При Create не добавляйте `GET /offers/{id}`. Проверяйте формат полей,
  сохраняйте ошибки создания привязки. `offer_name` — только метаданные отображения.
- Название: 5–255 символов; GEO: один существующий двухбуквенный код.
- Домен/источник — первые активные в порядке API; прогрев и кэш до 60 секунд
  допустимы для доменов, источников и групп.
- При Create группы всегда читайте свежим `GET /groups?type=campaigns`:
  ищите в одном ответе сначала `FORTESTS`, затем `test_markovskiy_group`.
  Если обе отсутствуют, создавайте только последнюю. После архивирования группы не удаляйте.
- Создавайте campaign disabled, type=position, ip_ua, USD, cost_auto=true.
  Потоки последовательно: Flow 1 — выбранный GEO и Google HTTP redirect;
  Flow 2 — остальные посетители, выбранный оффер 100%, без фильтров/лендингов.
- Сохраняйте проверки до/после активации. Подтверждённый снимок сохраняйте без
  повторного импорта и перезаписи параллельно сохранённого состояния.
  Дополнительные потоки создаются только в Keitaro; сохраняйте их имена, не фиксируйте ID.
- Выбор существующей кампании очищает поля/ошибки создания; сообщения формы
  не попадают в карточку. Неизвестный результат храните отдельно до сверки.
  В карточке нет строки GEO/Offers.
- Удаление — архив через `DELETE /campaigns/{id}`. Никогда не используйте
  `/campaigns/clean_archive` для одной кампании.

## Обязательные условия: редактор

- При каждом входе список пуст до Fetch streams from KT; состояние БД не очищайте
  и сохранённые потоки автоматически не загружайте.
- Список офферов загружайте при первом фокусе и переиспользуйте во всех потоках
  до выхода из редактора, включая пустой результат. После ошибки разрешайте повтор;
  при новом входе загружайте заново.
- Потоки с известными офферами (включая архив) показывайте первыми, внутри групп —
  порядок Keitaro, fallback имени — Flow N по позиции.
- Add/Remove/Bring back сохраняют черновик в БД. Remove оставляет серую архивную
  строку с 0%; последний оффер удалять разрешено, публикация `offers=[]` допустима.
  Bring back возвращает привязку; сам объект оффера не удаляется.
- Дубликаты запрещены; архивные возвращайте через Bring back. Add/Bring back
  проверяют доступность и активность оффера через API.
- Активные целые доли дают 100%; остаток распределяйте в стабильном порядке.
  Отображайте положительные доли выше архивных; сортировка не меняет округление.
- Pin закрепляет текущую долю без ручного ввода: вне черновика — метаданные БД
  без публикации, внутри — отменяется с ним. Remove снимает pin, возврат без pin.
  Учитывайте `allocation_error` и блокировку публикации.
- Импорт принимает фактические доли без пересчёта и автосоздания черновика;
  пропавшие известные привязки архивирует. Существующий черновик сохраняйте,
  внешние изменения вызывают конфликт и блокируют публикацию до разрешения.
- Push меняет только `offers` выбранного потока, с GET до и после PUT.
  Сохраняйте ownership, expected_revision, блокировки БД и HTTP 409.
  Не обещайте атомарный CAS: внешняя гонка между GET и PUT остаётся.

## Ошибки и неопределённый результат

- Не заменяйте ошибки Keitaro успехом; при частичном/неизвестном создании
  сохраняйте известный campaign_id и данные для сверки.
- Не повторяйте автоматически изменяющие запросы после таймаута: сначала чтение.
  UUID в Idempotency-Key/alias не гарантирует безопасный повтор POST.
- Не теряйте черновики, ревизии и намерение публикации. Намерение сохраняйте до PUT;
  после timeout/краша результат выясняется чтением/синхронизацией через
  `2*timeout+10` секунд от начала. Для missing-потока сохраняйте отмену после сверки.
- Не добавляйте отдельный журнал операций вне состояния публикации потока.

## Проверки и окружение

- Тесты, их инфраструктура и Ruff без запроса пользователя не добавляйте/не запускайте их и не устанавливайте зависимости для них.
- Выполняйте подходящие изменению проверки; для небольших правок достаточно сборки
  или проверки кода. Сообщайте только действительно выполненные проверки и результаты.
- Допустимые команды из корня:
  - `npm --prefix frontend run build`
  - `venv/bin/python -m compileall -q backend/app backend/migrations`
  - `git diff --check`
  - `docker compose up -d --build` (миграции автоматически)
  - `docker compose up -d --build --no-deps frontend`
  - `docker compose ps`
- Python-окружение — `venv`, не `.venv`. Frontend: localhost:8080, backend:8000,
  Vite:5173, PostgreSQL:127.0.0.1:55432 (POSTGRES_PORT).
- Не создавайте реальные кампании ради оформления. Если агент создаёт кампанию
  для функциональной проверки, имя начинается с `test_markovskiy_`;
  после проверки агент её архивирует. Это не ограничение имён рабочих кампаний пользователя.

## Секреты и данные

- Не выводите `.env`, API-ключи, POSTGRES_PASSWORD и DATABASE_URL в логи, Git
  или сообщения. Ключ Keitaro используется только backend.
- Храните в Git исходники, миграции, Docker-конфигурацию, README, AGENTS.md,
  requirements.txt и package-lock.json. Зависимости, сборки, кэши, логи,
  данные PostgreSQL и бэкапы должны игнорироваться.
- Не удаляйте том `postgres_data` и не меняйте трекер/БД без соответствующей задачи.
