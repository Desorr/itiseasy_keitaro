# Менеджер кампаний Keitaro

Приложение создаёт кампании через Keitaro Admin API и редактирует привязки офферов к потокам. Трафик распределяет Keitaro. PostgreSQL хранит состояние приложения, черновики, закрепления и архив привязок.

Backend: Python 3.11, FastAPI, httpx, SQLAlchemy AsyncSession, asyncpg, Alembic. Frontend: React, TypeScript, Vite. Интерфейс и сообщения об ошибках — на английском языке.

## Первый запуск после скачивания с GitHub

### 1. Установите необходимые программы

- [Git](https://git-scm.com/install/) — выберите свою операционную систему и установите Git.
- [Docker](https://docs.docker.com/get-started/get-docker/) — для macOS/Windows установите Docker Desktop и запустите его. Для Linux можно использовать Docker Engine с плагином Docker Compose.
- Получите адрес своего Keitaro-трекера и API-ключ в его административной панели.

Для запуска через Docker отдельно устанавливать Python, Node.js, npm или PostgreSQL не нужно: они работают внутри контейнеров.

Откройте Terminal на macOS/Linux либо PowerShell на Windows и проверьте:

```sh
git --version
docker --version
docker compose version
docker info
```

Команды должны завершаться без ошибок. Если Docker сообщает, что не может подключиться к daemon, запустите Docker Desktop/службу Docker и дождитесь готовности. На Linux у пользователя должны быть права обращения к Docker.

### 2. Клонируйте репозиторий

Перейдите в папку, где хотите хранить проект, затем выполните:

```sh
git clone https://github.com/Desorr/itiseasy_keitaro.git
cd itiseasy_keitaro
```

Если репозиторий закрытый, используйте учётную запись GitHub с доступом к нему. Все следующие команды Docker выполняйте из папки `itiseasy_keitaro`, где лежит `docker-compose.yaml`.

### 3. Создайте файл конфигурации

Создайте файл с точным именем `.env` в корне проекта, рядом с `docker-compose.yaml`. Это локальный файл: после клонирования его нет, поскольку он исключён из Git.

На macOS/Linux можно открыть редактор командой:

```sh
nano .env
```

На Windows:

```powershell
notepad .env
```

Вставьте следующий текст и замените шаблонные значения своими. Убедитесь, что редактор не сохранил файл как `.env.txt`.

```dotenv
KEITARO_BASE_URL=https://your-tracker.example
KEITARO_API_KEY=replace_with_api_key
KEITARO_TIMEOUT_SECONDS=20
POSTGRES_DB=keitaro
POSTGRES_USER=keitaro
POSTGRES_PASSWORD=replace_with_random_hex_password
POSTGRES_PORT=55432
DATABASE_URL=postgresql+asyncpg://keitaro:replace_with_random_hex_password@127.0.0.1:55432/keitaro
```

Что указать:

| Переменная | Значение |
|---|---|
| `KEITARO_BASE_URL` | HTTPS-адрес вашего трекера вместо `https://your-tracker.example`. Окончания `/admin`, `/admin_api` и `/admin_api/v1` нормализуются. |
| `KEITARO_API_KEY` | Ваш API-ключ Keitaro вместо `replace_with_api_key`. |
| `KEITARO_TIMEOUT_SECONDS` | Таймаут запроса к Keitaro: по умолчанию 20 секунд, допустимо больше 0 и до 120 включительно. |
| `POSTGRES_DB` | Имя БД приложения; можно оставить `keitaro`. |
| `POSTGRES_USER` | Имя пользователя БД; можно оставить `keitaro`. |
| `POSTGRES_PASSWORD` | Придумайте отдельный пароль БД и замените `replace_with_random_hex_password`. |
| `POSTGRES_PORT` | Локальный порт PostgreSQL; по умолчанию 55432. |
| `DATABASE_URL` | Локальная строка подключения: имя пользователя, пароль, порт и имя БД должны совпадать со значениями выше. |

Для пароля удобно использовать случайную hex-строку. На macOS/Linux её можно получить командой `openssl rand -hex 24`. Если используете специальные символы в пароле, в `DATABASE_URL` их необходимо URL-кодировать. В Compose строка подключения формируется из `POSTGRES_*`, поэтому hex-пароль упрощает настройку.

В nano сохраните файл через Ctrl+O, Enter, затем выйдите через Ctrl+X. В Блокноте сохраните через Ctrl+S и закройте редактор. Не публикуйте `.env`, API-ключ и пароль в GitHub.

Ключу нужны права чтения кампаний, потоков, офферов, доменов, источников и групп; создания кампаний, потоков и резервной группы; активации и архивирования кампаний; обновления привязок потоков. Доступ к кампаниям сам по себе не подтверждает доступ к офферам.

### 4. Соберите и запустите приложение

Из корня проекта:

```sh
docker compose up -d --build
```

Первый запуск требует интернета для загрузки Docker-образов и зависимостей. Дождитесь завершения команды, затем проверьте контейнеры:

```sh
docker compose ps
```

Должны работать три сервиса: `postgres`, `backend`, `frontend`. PostgreSQL и backend имеют проверки готовности и после запуска должны получить статус healthy.

Compose автоматически создаёт БД при первом запуске PostgreSQL, применяет миграции `alembic upgrade head`, запускает backend и после его готовности frontend. Вручную создавать таблицы или устанавливать зависимости внутри контейнеров не требуется.

### 5. Откройте приложение

- [Приложение](http://localhost:8080)
- [Swagger API](http://localhost:8000/docs)
- [Проверка backend и БД](http://localhost:8000/api/health)

При входе приложение покажет сохранённые кампании и запустит синхронизацию с Keitaro. Если своих кампаний ещё нет, откроется форма создания. Проверка health проверяет БД и наличие конфигурации, но не доступность Keitaro или права ключа.

Все порты Compose привязаны к `127.0.0.1`; инструкция рассчитана на открытие сайта на том же компьютере, где запущен Docker. Nginx обслуживает frontend и проксирует `/api/` на backend. API-ключ используется только backend и не передаётся браузеру.

### Остановка, повторный запуск и обновление

Остановить контейнеры с сохранением данных:

```sh
docker compose down
```

Повторно запустить:

```sh
docker compose up -d
```

Получить опубликованные изменения с GitHub и пересобрать приложение:

```sh
git pull --ff-only
docker compose up -d --build
```

Если Git сообщает о локальных изменениях или расхождении веток, сначала разберите их; не сбрасывайте рабочие файлы автоматически. После изменения `.env` также выполните `docker compose up -d --build`, чтобы backend получил новые настройки.

### Если запуск не удался

Посмотрите состояние и последние сообщения сервисов:

```sh
docker compose ps
docker compose logs --tail=100 backend
docker compose logs --tail=100 frontend
docker compose logs --tail=100 postgres
```

- Ошибка обязательной переменной Compose: проверьте, что `.env` находится рядом с `docker-compose.yaml`, переменные названы правильно и заполнены.
- Занят порт 55432: измените `POSTGRES_PORT` и порт в локальном `DATABASE_URL`, затем повторите запуск. Порты frontend/backend задаются в `docker-compose.yaml` (8080 и 8000).
- Ошибка доступа к Keitaro: проверьте адрес, ключ и права на конкретные объекты. Ошибки соединения, 401/403 и пустой список офферов нужно проверять отдельно от готовности БД.
- После смены пароля БД backend не подключается: `POSTGRES_*` инициализируют PostgreSQL при создании пустого тома, а не меняют существующего пользователя. Для существующей БД пароль меняется отдельно; не удаляйте данные ради перезапуска.

Данные PostgreSQL хранятся в именованном томе `postgres_data`. Обычный `docker compose down` сохраняет его; `docker compose down -v` удаляет данные и для обычной остановки не нужен. Смена Keitaro-трекера требует отдельной БД: сохранённые ID относятся к конкретному экземпляру Keitaro.

Внутри Compose backend подключается к сервису `postgres` на порту 5432. Настройка `DATABASE_URL` из примера используется при локальном запуске Python с подключением к опубликованному порту `127.0.0.1:55432`.

## Загрузка кампаний и офферов

При входе список кампаний сначала читается из PostgreSQL через `GET /api/campaigns`. Затем запускается фоновая синхронизация с Keitaro; сохранённый список доступен во время обновления. Индикатор — `Syncing with Keitaro…`. `Refresh` запускает синхронизацию вручную. При ошибке отображается сообщение и сохраняются доступные данные БД.

Синхронизация импортирует только кампании приложения: принадлежность определяется alias вида `tm_<16 hex>`. Обновляются также потоки и известные привязки. Архивные кампании скрываются из списка.

При каждом открытии формы создания свежий список активных офферов асинхронно запрашивается через `GET /api/offers`. Backend читает его из Keitaro API, а не из БД. Постоянного кэша офферов нет; браузерный запрос использует `cache: no-store`. Пока пользователь вводит название и GEO, список загружается. Поиск в форме выполняется локально только по цифрам ID, выбор из dropdown обязателен. При ошибке доступна `Retry`. Закрытие формы отменяет её загрузку, устаревшие ответы игнорируются.

При выборе существующей кампании очищаются поля и ошибки формы создания. Информация о запросе создания с неизвестным результатом сохраняется отдельно для проверки. В карточке кампании нет строки GEO/Offers. `Add campaign` открывает форму; в редакторе эта кнопка скрыта.

## Создание кампании

Поля: название 5–255 символов после удаления крайних пробелов, один существующий двухбуквенный GEO-код и выбранный оффер. Формат проверяется на frontend и backend. Frontend передаёт `offer_id` и необязательное `offer_name`; название служит для отображения в БД. Дополнительного `GET /offers/{id}` при Create нет. Ошибки Keitaro при создании привязки показываются пользователю.

При открытии сайта `GET /api/campaigns/preparation` заранее параллельно загружает домены, источники и группы. Кэш этих справочников в памяти backend действует до 60 секунд. При Create:

- Домен и источник выбираются первыми активными в порядке ответа API. Используется кэш, а после его истечения — новый запрос.
- Список групп читается свежим `GET /groups?type=campaigns`, независимо от прогрева. В одном ответе сначала ищется `FORTESTS`, затем `test_markovskiy_group`: отдельного GET для каждой группы нет. Если обе отсутствуют, создаётся только `test_markovskiy_group` дополнительным POST-запросом. При неопределённом результате создания группы выполняется чтение для сверки, без автоматического повтора POST.

Порядок создания:

1. Создать выключенную кампанию: `type=position`, `uniqueness_method=ip_ua`, `cost_currency=USD`, `cost_auto=true`.
2. Последовательно создать `Flow 1` и `Flow 2`, оба regular. Первый фильтрует выбранную страну и делает HTTP-редирект на `https://google.com`. Второй без фильтров и лендингов направляет остальных на выбранный оффер с долей 100%.
3. Прочитать и проверить настройки кампании и потоков, активировать кампанию, повторно прочитать и подтвердить результат. В каждой проверке кампания и потоки читаются параллельно.
4. Сохранить подтверждённые данные в PostgreSQL без повторного импорта из Keitaro. Если параллельная синхронизация уже сохранила кампанию, её состояние не перезаписывается снимком создания.

Фиксированных Keitaro ID нет. Дополнительные потоки создаются только в Keitaro; импорт сохраняет их фактические имена. Старые потоки автоматически не переименовываются.

`POST /api/campaigns` требует `Idempotency-Key` с UUID, из первых 16 шестнадцатеричных символов которого формируется alias `tm_<16 hex>`. Это идентификатор для выяснения результата, а не разрешение автоматически повторять POST. Незавершённый запрос сохраняется в `sessionStorage`; при частичном создании ошибка содержит известный `campaign_id`. Если результат неизвестен, сначала нужно проверить его чтением/синхронизацией.

Alias — адресный идентификатор кампании в трекинговой ссылке, а не API-ключ или секрет; он не даёт прав доступа. Числовой `id` используется в API-путях, а alias — для распознавания кампаний приложения и поиска результата незавершённого создания.

## Редактор потоков

`Edit` открывает редактор с пустым списком. Данные появляются только после `Fetch streams from KT`; черновики и архив в БД при этом сохраняются. Сначала показываются потоки с известными офферами, включая архивные, затем потоки без офферов. Внутри групп сохраняется порядок Keitaro; пустое имя заменяется на Flow N по позиции. Потоки без известных офферов показываются без редактирования редиректов и фильтров.

Редактируются привязки в потоках со схемой `landings` и известными офферами. Название кампании, GEO и остальные настройки потоков в редакторе не меняются.

| Действие | Результат |
|---|---|
| `Add` | Выбрать активный оффер по ID и добавить в черновик. Для архивного используется Bring back, дубликаты запрещены. |
| `Remove` | Оставить серую строку с 0% в архиве. Можно убрать последний оффер и опубликовать пустой массив привязок. Сам объект оффера не удаляется. |
| `Bring back` | Вернуть архивную привязку без закрепления; доступность и активность оффера проверяются через Keitaro API. |
| `Pin` / `Unpin` | Закрепить текущую долю без ручного ввода. Вне черновика это только метаданные БД; внутри черновика изменение отменяется вместе с ним. |
| `Push to KT` | Опубликовать только массив `offers` выбранного потока и подтвердить результат GET-запросом. |
| `Cancel` | Удалить черновик и принять последнее подтверждённое состояние. |

В редакторе список выбора офферов запрашивается при фокусе соответствующего поля; поиск по ID локальный. Добавление и возврат отдельно проверяют активность выбранного оффера на backend.

Изменённый поток жёлтый, доступны Push to KT и Cancel. При изменении состава свободный процент делится поровну между незакреплёнными активными офферами. Доли целые, остаток распределяется в стабильном порядке: например, 34/33/33. При наличии активных офферов сумма равна 100%; без них доли равны 0%. Удаление снимает закрепление. Если закрепления мешают распределению, действие отклоняется; при `allocation_error` публикация недоступна.

Офферы с положительной долей показываются выше, архивные строки — ниже. Сортировка отображения не меняет порядок округления. Черновики, архив и закрепления сохраняются после перезапуска.

## Синхронизация и неопределённый результат

Импорт принимает фактические доли Keitaro без пересчёта и без автоматического черновика. Пропавшие известные привязки остаются в архиве с 0% и Bring back. Уже существующий черновик сохраняется. Если Keitaro изменился относительно его исходного состояния, появляется конфликт, публикация блокируется до отмены черновика и принятия подтверждённых данных.

Ревизии и транзакционные блокировки PostgreSQL защищают от одновременных изменений из вкладок. Устаревшая ревизия возвращает HTTP 409. Перед публикацией проверяются принадлежность кампании, актуальность потока, доли и новые офферы. В Keitaro нет атомарного CAS: внешняя запись между проверкой и PUT остаётся возможной.

Намерение публикации фиксируется в БД до PUT. После таймаута/прерывания запись автоматически не повторяется. Повторная публикация и Cancel блокируются до сверки. Для прерванной операции сверка разрешается через `2 × KEITARO_TIMEOUT_SECONDS + 10` секунд от начала публикации, по умолчанию через 50 секунд. Её запускает чтение состояния или синхронизация; отдельного фонового планировщика нет. Совпавший результат подтверждается, иначе черновик сохраняется; внешнее изменение вызывает конфликт. Исчезнувший поток отмечается как missing, его черновик можно отменить после завершения сверки.

Keitaro и PostgreSQL не образуют общую транзакцию. Ошибки не заменяются успехом; сведения о частичном или неопределённом результате сохраняются для проверки. Отдельного журнала операций вне состояния публикации потока нет.

Удаление кампании — архивирование через `DELETE /campaigns/{id}`, с проверкой принадлежности приложению и результата. В интерфейсе используется диалог Remove/Cancel. В БД сохраняется история, группа и объекты офферов не удаляются. `/campaigns/clean_archive` не используется: он очищает весь архив Keitaro.

## Данные и структура проекта

| Таблица | Назначение |
|---|---|
| `campaigns` | ID, alias, статус и JSONB-данные кампаний приложения. |
| `offers` | ID и названия известных офферов для отображения и архива, не источник dropdown. |
| `streams` | Порядок, схема, подтверждённое состояние, JSONB-черновик, ревизия, конфликт, missing и намерение публикации. |
| `stream_offers` | Привязки, порядок, доли, статус, закрепление и признак архива. |

Backend: `main.py` — маршруты и lifecycle, `keitaro.py` — HTTP-клиент и кэш справочников, `services.py` — создание и архивирование, `editor.py` — импорт и редактор, `database.py` — модели/подключение, `schemas.py` — контракты, `config.py` — настройки. Миграции — `backend/migrations`.

Frontend: `App.tsx` — список и создание, `CampaignEditor.tsx` — редактор, `OfferPicker.tsx` — выбор оффера в редакторе, `api.ts` — клиент/типы, `style.css` — оформление.

|---|---|
| `GET /api/health` | Проверка БД и наличия конфигурации. |
| `GET /api/offers?query=…` | Активные офферы из Keitaro; необязательный серверный поиск по ID или имени. |
| `GET /api/campaigns/preparation` | Прогрев справочников, ответ `{ "ready": true }`. |
| `GET /api/campaigns` | Список из PostgreSQL. |
| `POST /api/campaigns/sync` | Синхронизация кампаний приложения и потоков. |
| `POST /api/campaigns` | Создание; обязателен заголовок Idempotency-Key. |
| `DELETE /api/campaigns/{id}` | Архивирование кампании. |
| `GET /api/campaigns/{id}/streams` | Сохранённое состояние редактора, при необходимости сверка прерванной публикации. |
| `POST /api/campaigns/{id}/streams/sync` | Импорт потоков из Keitaro. |
| `PATCH /api/campaigns/{id}/streams/{sid}/draft` | Действие add/remove/restore/toggle_pin, offer_id и expected_revision. |
| `DELETE /api/campaigns/{id}/streams/{sid}/draft` | Отмена с expected_revision в JSON-теле. |
| `POST /api/campaigns/{id}/streams/{sid}/publish` | Публикация с expected_revision в JSON-теле. |

Ответы `GET /api/campaigns` и `POST /api/campaigns/sync` — массивы `CampaignSummary`; ответ `POST /api/campaigns` — один `CampaignSummary`. В каждом объекте только `id`, `name`, `alias`, `state`. Alias нужен frontend для восстановления запроса создания. Домены, группы, источники, GEO, офферы, ID потоков и ссылки из внутреннего снимка кампании не возвращаются в этих ответах; они сохраняются на backend. Данные потоков для редактора выдаются отдельными эндпоинтами.

В Swagger эндпоинты сгруппированы по System/Offers/Campaigns/Flows; указаны схемы успешных ответов и ошибок, required Idempotency-Key, expected_revision и поведение при неопределённом результате. `/docs` и `/openapi.json` доступны на backend (порт 8000). Нажатия Try it out / Execute для изменяющих методов выполняют реальные операции в Keitaro или БД.

Точные схемы — в Swagger. Ошибки Keitaro содержат `code`, `message`, `uncertain`, `campaign_id`. Ошибки валидации возвращаются отдельно в `detail`.

## Проверки и Git

Автотесты, тестовая инфраструктура и Ruff удалены по требованию проекта. Без отдельного запроса их не добавляют и не запускают. Разрешённые проверки из корня:

```sh
npm --prefix frontend run build
venv/bin/python -m compileall -q backend/app backend/migrations
git diff --check
```

Применение frontend: `docker compose up -d --build --no-deps frontend`. Полная пересборка: `docker compose up -d --build`.

Меняющие функциональные проверки выполняются только с префиксом кампаний `test_markovskiy_`; созданные для проверки кампании затем архивируются. Для проверки оформления реальные кампании не создаются.

В Git сохраняются исходники, README, AGENTS.md, Docker-конфигурация, миграции, `backend/requirements.txt` и `frontend/package-lock.json`. `.gitignore` исключает секреты, зависимости, сборки, кэши, логи и локальные данные/бэкапы PostgreSQL. `.env.example`, если добавляется, должен содержать только шаблонные значения. Коммит и push выполняются по запросу пользователя.
